# Proxmox Cluster & Node Discovery — 0.6.2

## Upgrade and setup

Stop connector workers and scheduler; back up PostgreSQL and application files. Overlay the release on 0.6.1 and run `php bin/cajeer migrate` (0038). Existing migrations are unchanged. Run `php scripts/verify-release.php` and `php bin/cajeer collection:doctor --json` on your configured server.

Use a configured PVE 8/9 Connector Target with the TLS profile from 0.6.1, an active Inventory asset, and a Vault API token. The profile must already be confirmed using trusted certificates and cluster identity. Use scoped read-only privileges: `Sys.Audit` at `/` for `/cluster/status` and `Sys.Audit` on the visible nodes for `/nodes/{node}/status`; do not grant `VM.PowerMgmt` just to collect hardware. The endpoints are documented by the upstream PVE API viewer (`https://pve.proxmox.com/pve-docs/api-viewer/`).

Create a plan in `/collections` → «Планы и запуски»: collector `proxmox.cluster`, operation `inspect` or `sync`, interval e.g. 300 seconds, TTL e.g. 86400 seconds. Confirm with MFA and use the existing Scheduler and Connector Worker (`php bin/cajeer scheduler:run`, `php bin/cajeer connector:work 20`). Manual queue runs with a matching ordinary inspect/sync service grant are supported as well. No new service is required. The existing `proxmox.inventory` collects guests, and `proxmox.metrics` collects time series; cluster discovery intentionally does not call either.

## Collection behavior

Each attempt uses one verified endpoint and the existing TLS, DNS pinning, certificate pin and version/anchor checks. It projects the already-fetched `/cluster/status` into cluster and node membership. It reads `/nodes` and `/nodes/{node}/status` only for visible online nodes. The membership response reports the cluster name, quorum, corosync config version, count, member IDs and local/online flags; optional votes are recorded only when provided by the API. Standalone PVE produces one node, no synthetic cluster. Never uses member IPs to add connection endpoints.

The node status response is projected into PVE version, CPU model, cores, sockets, logical CPUs, CPU utilization, uptime, memory, swap and root filesystem. Byte counts are exact decimal strings. Unknown fields are ignored, never stored raw. Node metadata is bounded to 256 members, and detailed reads use a shared 60-second budget (in-flight request may run until its transport deadline). Large clusters rotate the order across minute boundaries; this is best-effort, not a guarantee of a complete detail sweep at each tick. HTTP 403/404/5xx on a node status is represented as unavailable details; 429 stops further detail requests. Invalid response, 401, TLS/trust errors fail the attempt; transport failure can trigger existing whole-read failover, not mixing partial responses from different endpoints. Base membership/list errors do not update current state. A membership/list inconsistency fails rather than inventing an unknown node. A disagreement in online state produces unknown.

`inspect` persists the current cluster snapshot and connector run without modifying Inventory. `sync` additionally uses Reconciliation to create/update `cluster:<name>` and `node:<name>` observations, retaining existing node UUIDs and linking nodes to the cluster via `parent_external_id` in connector-discovered topology. Manual Inventory field provenance and conflict resolution remain intact. This is not an automatic write to manually managed `cluster_contains` relationships. Both cluster and ordinary PVE inventory snapshots are partial: a successful ACL-filtered response does not establish resource absence. No deletion, absence counter advancement or status changes for unreported resources. Other provider behavior is unchanged.

## Current snapshot and history

`GET /api/v1/connectors/targets/{id}/proxmox-cluster` (session, `connectors.targets.read`, `inventory.assets.read`, Workspace membership). Returns `{data:{state,observed_at,snapshot}}`: `not_collected`, `available`, or `stale` after a target/profile/binding revision change, credential deactivation or target disable. `available` means a stored observation, not live health; check the timestamp and run history. The snapshot includes `cluster`, `standalone`, `membership_scope: reported_only`, `member_count`, `visible_node_count`, `reported_node_count_mismatch`, `details_complete` and `nodes`. `details_complete` means every reported member returned some supported detail, not that every possible field is available. Each node has `details_state`, `details`, `last_details` and `last_details_observed_at`. Current state may carry the previous details only for the same target/credential revision and same node identity; never label those as fresh. Members no longer reported disappear from the current reported membership, but remain in previous runs and Inventory. Revisions invalidate the current view; older snapshots remain historical.

Writes occur in the same guarded transaction as connector run completion (and Inventory sync, if requested), so cancellation, revoked grant, stale profile and rollback cannot publish a new state. Current state is kept in `proxmox_cluster_state`; individual snapshots and attempt history use existing `connector_runs` and `collection_run_attempts`. `GET .../runs?collector=proxmox.cluster&limit=20&offset=0` filters history; individual `GET .../runs/{runId}` includes `result.connection.cluster_discovery.nodes`. Lists omit node details for bounded response size. UI shows the current/last-known data and historical snapshots under `/collections` → «Коллекторы» for PVE targets. Existing run export includes stored snapshots. TypeScript SDK: `client.proxmoxCluster(targetId)` and `client.runs(targetId,50,0,undefined,'proxmox.cluster')`.

## Tests and limits

`php tests/proxmox-cluster-smoke.php` exercises the actual collector, validation, partial state and last-known merge. `python3 tests/proxmox-profile-https-integration.py` uses two real TLS fixtures with membership, node status, failures, quorum and failover. `tests/proxmox-profile-postgres-integration.php` extends the upgrade scenario to 0038, plan/worker execution, stable UUIDs, existing guests, partial state and history, and ACL/profile fencing. Run it with the existing isolated `CAJEER_PG_TEST` setup. `php scripts/verify-release.php --strict` is required for production qualification. Fixtures do not substitute for real PVE 8/9 clusters or PostgreSQL integration. No snapshot actions, guest configuration or generic topology writes are introduced in this version.
