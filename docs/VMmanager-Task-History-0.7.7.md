# VMmanager Task History & Events — 0.7.7

`vmmanager.tasks` — read-only Inspect collector for VMmanager 6 Hosting/Infrastructure API v3. It uses the existing HTTPS transport, pinned leaf certificate, anchor node and Vault token, with `auth/v4/whoami` before and after discovery. It never calls remote mutation endpoints. The documented task endpoint and status meanings are described in [ISPsystem API examples](https://www.ispsystem.ru/docs/vmmanager-admin/razrabotchiku/primery-ispol-zovaniya-api-v2026052) and [API filters](https://www.ispsystem.ru/docs/vmmanager-admin/razrabotchiku/rabota-s-api-v2026052).

## Installation and operation

1. Stop workers, apply changed files and `php bin/cajeer migrate` (0051); rebuild Admin UI and restart workers.
2. Configure a VMmanager target with a verified TLS profile and Vault API credential. The remote token must read node, task and whoami. The existing collection-grant permissions, MFA and Workspace checks apply.
3. Create an Inspect collection plan `vmmanager.tasks` under Collections → Plans and runs. Recommended interval 60 seconds, service grant with sufficient lifetime. Run it. In Collectors the VMmanager task history panel has task/event views, state filter, next/previous pages, last observation and cursor progress. SDK `vmmanagerTasks` / `vmmanagerTaskEvents` read the same endpoint.

## Incremental and durability semantics

- Each run reads at most 5 new pages of 100 rows ordered by remote numeric ID (`id GT cursor`), up to 20 old nonterminal records with exact ID matching and one old-history sweep page. The cursor advances only on successful normalized pages and only in the transaction that saves tasks, events and job result. An empty page (not a short page) demonstrates exhaustion at that observation; `caught_up` is not a guarantee of full historical visibility. The rolling sweep revisits earlier IDs to discover late-visible records. No whole-history result is required for progress; the runtime's existing 60-second deadline applies. If any request fails, the whole batch is discarded, and retry resumes from the committed cursor.
- `created` → `queued`, `deferred` → `deferred`, `running` → `running`, `complete` → `succeeded`, `fail` → `failed`, anything else → `unknown`. Missing tasks are marked `not_visible` in check diagnostics, not treated as completed/deleted. Terminal evidence is never downgraded. Events record discovery and observed transitions (including queued/deferred/running cycles, completion and clarification of unknown), not every poll. Sequence numbers make repeated observations and retries idempotent. No event implies a real remote transition time: timestamps are local observations. `consul_id` is distinct from remote numeric ID. Resource association is optional and comes only from an explicit host reference, not task parameters.
- Data scope is target ID + target version + credential ID/version. Current read requires active target, current binding and active credential/asset. Profile changes or rotation invalidate the visible scope; the old history is not returned by this endpoint. The saved cursor also fences changed remote principal/administrator status; use a new credential revision if remote identity changes. Retained history is observation-based, not an authoritative current ACL query; token changes are not automatically detected without a collection run. Task retention on VMmanager and gaps before first observation limit completeness. There is no automatic local retention; deleting the target cascades its history.
- Only allowlisted metadata is persisted. Raw task params, output, logs, remote error text and secrets are discarded. No task cancellation, start/stop, notification delivery or action reconciliation yet. The new collector never reconciles CMDB absence.

## Verification

`python3 tests/vmmanager-https-integration.py` exercises the production driver on a local TLS fixture, including cursor continuation, late visibility, ACL, status mapping, missing pending records and terminal preservation. `CAJEER_PG_TEST=1 ... python3 tests/vmmanager-https-integration.py --postgres` additionally uses the existing disposable PostgreSQL test configuration to run migrations, authorized Vault/worker execution, pagination and transactional event/cursor consistency. Use only a dedicated `cajeer_test_*` database. This is a synthetic fixture, not a live VMmanager certification.
