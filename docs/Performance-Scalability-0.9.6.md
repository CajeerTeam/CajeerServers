# 0.9.6 — Performance & Scalability

## Runtime changes

Inventory keeps its exact-total API by default. `GET /api/v1/inventory/assets?workspace_id=UUID&limit=50&include_total=0` skips the count and returns `total: null`, `pagination.total: null`, `pagination.has_more` and `pagination.next_cursor`. For `sort=created_desc`, send `cursor` with `offset=0` to continue; the cursor is derived from the last returned `(created_at,id)` tuple. The existing offset ceiling of 10000 remains for non-default sorts. Cursor traversal is not a cross-request database snapshot: concurrent mutations may affect membership in the filtered set. Each query rechecks workspace membership and active user status. Admin uses the count-free mode, with previous/next keyset navigation for creation order and bounded offsets for other sorts. Exact totals remain available through API.

EventStore writes up to 200 normalized events in one parameterized JSONB INSERT, ordered by input ordinal. Target locking, duplicate identity, cursor fencing, quota and transactional rollback remain unchanged. Search by interface IP is now a workspace-scoped set subquery rather than a correlated asset subquery. Metric ingestion skips the workspace series count only when all identities already exist; new series still pass the locked quota check. Stable statement-time cutoffs aid indexed retention/partition scans.

Migration `0064_performance_scalability.sql` builds nine indexes for active assets, groups, events, metric series and provider-filtered connector pages. It runs offline inside the existing upgrade transaction. On a large database, provision space for indexes and WAL and schedule a maintenance window. Index builds take locks; no historical migrations or records are rewritten. Use `EXPLAIN (ANALYZE, BUFFERS)` on a restored staging copy to confirm plans; extra indexes consume storage and increase write cost.

## PostgreSQL load test

Use a disposable `cajeer_test_*` database on PostgreSQL 17/18, a role that can create a schema and required extensions, PHP with pdo_pgsql, and the existing test configuration variables (`CAJEER_PG_TEST_HOST`, `PORT`, `DATABASE`, `USERNAME`, `PASSWORD`, `SSLMODE` with prefix `CAJEER_PG_TEST_`). Never use production. The benchmark creates a randomly named schema, runs all migrations, seeds deterministic assets/targets/metric samples/events (history triggers stay enabled), verifies keyset and batch idempotency, then launches independent PHP processes and connections. It drops only the generated schema in finally; an abrupt kill may leave that schema for manual cleanup. Extension installation may persist in the disposable database. The sample metric points are historical and generated by SQL, not live connector traffic. Each run records separate p50/p95/p99/max by operation, successful queries/second, PostgreSQL settings, PHP version and peak worker PHP memory. A nonzero exit means a failed worker, invariant, cleanup or optional latency threshold. Default CI profile is small and has no timing gate (shared runners vary).

```sh
export CAJEER_PG_TEST=1 CAJEER_PG_TEST_DATABASE=cajeer_test_perf
php scripts/benchmark-postgres.php --assets=1000 --targets=10 --samples=10000 --events=1000 --clients=2 --iterations=10
# Larger staged profile; size must fit PostgreSQL connection and storage limits.
php scripts/benchmark-postgres.php --assets=100000 --targets=1000 --samples=1000000 --events=100000 --clients=50 --iterations=100 --p95-ms=500 > performance.json
```

The benchmark is closed-loop; throughput includes process startup/warmup. Each iteration executes ten read paths, not ten HTTP requests. Exact count, count-free first page and deep keyset are measured separately; do not interpret the numbers as a controlled before/after comparison without running both versions under identical conditions. `--p95-ms` is opt-in; the proposed 500 ms budget is not a confirmed production SLO. PostgreSQL tests are part of CI and strict release verification.

## HTTP load test

Run only on an authorized staging deployment. No mutations, redirects, or credential logging. HTTPS required remotely, certificates verified. Optional `--cookie-file` is a private 0600 file containing a valid staging session Cookie header; obtain it through the normal login process and delete it after testing. The runner measures request/JSON response time and treats non-200 or malformed JSON as failures. Rate limits are not bypassed. Use individual test accounts/sessions in separate runs when measuring real concurrent users; one cookie simulates parallel requests, not independent users.

```sh
python3 scripts/benchmark-http.py --origin https://staging.example.test --authorized-staging \
  --path 'inventory=/api/v1/inventory/assets?workspace_id=UUID&limit=50&include_total=0' \
  --cookie-file /secure/staging-cookie --clients 20 --requests 2000 --p95-ms 500
```

Local evidence for this change: built-in PHP HTTP server, four configured worker processes (plus server parent), 8 concurrent clients, 1,000 requests to `/api/v1/live`, zero failures, p95 9.002 ms, p99 12.037 ms, 1577.13 requests/sec. This is a liveness/harness check only: no database, authenticated API, Nginx/FPM, Nuxt, queue or live device traffic was exercised. PostgreSQL 17/18 benchmark and full build require external environment; 24-hour soak and capacity certification are outstanding.

## Upgrade

Retain the complete previous 0.9.5 release and stop all writers before switching code. Use the existing `maintenance:enable`, `upgrade:apply --previous=/opt/cajeer-releases/0.9.5 --archive=/secure/pre-upgrade-0.9.5.cjdr --key-file=/secure/backup.key --offline`, `migrate:validate`, `inventory:integrity --json`, `maintenance:disable`, `health:ready`. Confirm PostgreSQL integration and inspect plans before production rollout. Release channel remains development.
