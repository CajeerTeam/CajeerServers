# Webhook & Event Data Ingestion (0.5.7)

## Setup

Migrate `0034_data_ingestion.sql` before restarting the web app or workers. Existing connector refresh webhooks are unchanged. New data ingestion is independent of network connector execution. Create an active connector target with a matching Inventory asset and Vault binding, issue an **unscheduled inspect** service grant using the existing MFA authorize-use flow, then create a source for that target. The grant's actor must have `ingestion.write`; creation and administration require `ingestion.manage`, reading requires `ingestion.read`, plus the existing target/Inventory permissions and workspace roles. An administrator is granted all three by migration. An active grant is mandatory even for a push-only producer; the worker does not decrypt or use the target's remote credential. A grant is tied to target/credential versions and expires in at most 30 days. Renew by creating a fresh grant and source; existing sources cannot be silently rebound. Source key is returned only on creation/rotation. Store it in a secret manager; never put it into a URL or log. `VaultKeyRotation` rewraps these keys.

## HTTP API

Prefix `/api/v1`. Administrative endpoints use session authentication; POST/DELETE require CSRF. Use `/connectors/targets/{id}/ingestion-sources` (GET/POST); POST `{grant_id,name,kind}` creates source, with kind `metrics`, `events`, or `observations`. `/ingestion-sources/{sourceId}/rotate` POST replaces key; DELETE `/ingestion-sources/{sourceId}` revokes. Source IDs are not authentication. Only the grant owner can rotate. Existing signed deliveries already accepted remain valid across rotation; revocation/expiry blocks processing not yet committed. Disable instead of deleting a target while source history is retained.

External POST `/connectors/ingestion/{sourceId}/batches`, `Content-Type: application/json`, `X-Cajeer-Timestamp` Unix seconds, `X-Cajeer-Signature: sha256=<hex>`.

Signature is HMAC-SHA256 over **exact bytes** `v1.<timestamp>.<lowercase-source-uuid>\n<raw body>`, using the issued 64-character hex string as UTF-8 key (do NOT hex-decode the secret). UTC clock skew <=300 seconds. HTTPS only in production, no redirects; configure the reverse proxy's own unauthenticated rate limit. Timestamp refers to the request, not measurement. Retry the same bytes and batch ID with a fresh timestamp/signature. HTTP 202 means only durable acceptance; use authenticated status to confirm processing. Duplicate bytes and ID return the original batch UUID/status; a different body with the same ID yields 409. Signature failures return 401. Schema validation 422, body >256 KiB 413, capacity/rate 429.

Example `batch.json` (replace timestamp with actual measurement UTC time):

```json
{"schema_version":1,"batch_id":"collector-001","kind":"metrics","records":[{"metric":"network.receive_bytes","value":"18446744073709551615","kind":"counter","unit":"bytes","resource_external_id":"eth0","labels":{"site":"dc1"},"observed_at":"2026-11-12T05:00:00Z"}]}
```

Run `CAJEER_INGESTION_SECRET=<issued-key> python3 examples/ingestion/send.py https://cajeer.example/api/v1 <source-uuid> batch.json --ca-file /etc/ssl/my-ca.pem`. Keep shell history clear of keys; prefer injected environment from a secret manager. The supplied sender refuses insecure URLs, redirects, oversized bodies and invalid certificates; never automatically regenerates a batch ID.

Metrics accept the existing MetricBatch schema, including numeric decimal strings (recommended for Counter64), optional `kind`, `unit`, `resource_external_id`, `labels`; explicit UTC timestamp required, within 30 days and at most 5 minutes into the future. A server assigned `cajeer_source` label and separate metric identity distinguish sources; callers cannot set that label. The existing metric series API exposes `ingestion_source_id`. MetricStore applies batch validation, series quotas, deduplication and atomic conflict detection. Pull series are not changed.

Events: `{event_id,type,message,severity,observed_at}`; severity debug/info/warning/error/critical (default info). Events are informational, never trigger commands or deletions. Same event ID and normalized content within one source deduplicate across batches; changed content fails entire batch. Observations: `{external_id,type,fields,observed_at}` uses existing DataNormalizer and Inventory ObservationInput; reserved connector identities and workspace/asset injection are rejected. Observation batches are **candidates only**, available via batch detail; applying them requires a separate authorized Inventory import. Events/observations timestamps follow existing DataNormalizer bounds (366 days past, 5 minutes future). No raw stdout or secrets should be sent as event messages.

Admin endpoints: GET `/connectors/targets/{id}/ingestion-batches?limit=50&offset=0`; GET `.../ingestion-batches/{batchId}` (normalized payload, result and attempts), POST `.../ingestion-batches/{batchId}/redrive` (failed only, 10 dispatches maximum). GET `.../data-events?limit=50&offset=0`. Lists are scoped to the target/workspace, omit raw signed bytes and secrets; detail includes normalized payload. The `/connectors` UI includes source management and history.

## Processing, retention and limits

Run `php bin/cajeer ingestion:work 20` periodically (supplied `cajeer-ingestion-worker.service`/`.timer`, default 5s). The worker processes one batch per transaction, with workspace row lock + `SKIP LOCKED`. No network or script calls; metric/event inserts and terminal status commit together. Process death rolls everything back (no external side effect to repeat). A savepoint rolls back an invalid batch without partial writes. Transient PostgreSQL lock/serialization/statement timeout failures retry with 30/60/120/240s delays, at most 5 attempts per dispatch. Terminal failed batches form the DLQ; redrive preserves previous attempt history and never changes payload. Grant and source authorization checked before and after writes. Unexpected database/system errors stop the worker with a nonzero exit; the transaction rolls back and the batch remains queued. Service restarts retry it; investigate recurring unexpected errors rather than silently dropping them. Source revocation prevents pending work from committing; work committed before revocation is retained.

Limits: 1000 records / 256 KiB raw / 512 KiB normalized per batch; 60 valid signed submissions/minute/source; 100 pending/source, 500 pending/workspace, 10,000 retained batches and 256 MiB normalized payload/workspace; 100,000 retained events/workspace; 10 active sources/target, 100 source records/workspace. Source metadata is retained for audit while any dependent data remains. Metric series quota remains 10,000/workspace. `ingestion:retain 1000` (supplied hourly timer) deletes finished inbox rows/attempts and stored events older than 30 days in bounded batches. Batch/event deduplication lasts while their records are retained; metric deduplication lasts while samples are retained. Metrics retain existing 30-day retention. Retention does not purge queued batches. It removes revoked sources after 30 days only when no inbox, event or metric series references remain; audit records remain. Explicitly revoke expired sources. No automatic application of observations, no Kafka or external queue dependency.
