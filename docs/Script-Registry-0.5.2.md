# Script Registry & Signed Templates — 0.5.2

## Update

Back up PostgreSQL and code, unpack the changed files over 0.5.1, stop old workers during upgrade, and run `php bin/cajeer migrate`. Migration `0030_script_registry.sql` adds scripts, immutable script versions, trusted Ed25519 public keys, and four RBAC permissions. No existing connector, Vault or Inventory data is replaced. `php scripts/verify-release.php` checks the source release; `--strict` also requires real dependencies and staging.

## Operator workflow

Use `/scripts` in the admin UI or `/api/v1/workspaces/{workspace}/scripts` via the existing authenticated session and CSRF token. Grant `scripts.read` to readers, `scripts.manage` to authors, `scripts.approve` to workspace owners (with MFA), and `scripts.execute` to users allowed to validate approved versions. The migration grants the four scopes to the administrator role; other roles must be explicitly configured. All resources are scoped to a workspace; membership is checked on every operation. Owners and managers may author, owners may trust keys and approve or revoke. Approval by the same author is permitted with fresh password/TOTP (no mandatory four-eyes policy in this version).

1. Create script metadata: POST the script collection with `name` and optional `description`. PATCH or DELETE (archive) uses the current `etag` from GET detail in `If-Match`.
2. Create a version: POST `/{id}/versions` with e.g. `{"language":"python","provider":"local","source":"print(42)","parameters":[{"name":"count","type":"integer","min":1,"max":10}]}`. A remote version must explicitly list `target_ids`; the server binds their current configuration revisions into the signed manifest. No local target is allowed. Source must be UTF-8, 1–65536 bytes. Timeout 1–90 seconds, output 1024–262144 bytes, JSON parser only. The limits are signed policy for the future executor, not enforced runtime limits on code in this release.
3. On a trusted offline workstation generate a signing key using `php bin/script-sign.php generate /secure/script.key`. It creates a new owner-only file and prints the public key (hex). Register that public key using POST `/keys` with name, public_key, password, totp. Never upload a private key. Key registration and revocation require fresh MFA.
4. GET `/{id}/versions/{version}` and review both `source` and `signing_bytes` (the UI shows the source and downloads the bytes). Verify that SHA-256 of source matches `source_sha256` in the signing bytes. Save the exact UTF-8 value of `signing_bytes` **without a newline or reserialization**, e.g. `jq -j '.data.signing_bytes' version-response.json > signing-bytes.json`. Review all execution settings and target scope before signing.
5. Run `php bin/script-sign.php sign /secure/script.key signing-bytes.json`. POST `/{id}/versions/{version}/sign` with `key_id` and detached `signature` hex. Invalid signatures are rejected; a successful signature changes draft to pending_review. The immutable version cannot be signed again or changed. Create another version to modify source/policy.
6. POST `/{id}/versions/{version}/approve` with fresh `password` and six-digit `totp`. A new TOTP must be used for each protected operation (login also consumes a code). The server checks the actual signature, digest, trust state and target revisions again before approval.
7. POST `/{id}/versions/{version}/validate` with `{ "parameters": { "count": 2 } }` (include `target_id` for remote versions). The response says `valid: true, execution_enabled: false`. This validates parameters and current eligibility; it does not run code or issue Vault grants. Use `scripts.execute` plus owner/manager membership. It never accepts caller-supplied workspace or asset identity inside parameters.
8. Revoke a version with POST `/{id}/versions/{version}/revoke` or revoke a key with POST `/keys/{id}/revoke` (fresh MFA). Revoking a key also revokes its pending and approved versions, in one transaction. Archiving prevents new versions, approval and eligibility. Audit records only metadata, not source, passwords or TOTP. Revocation is irreversible. Old versions remain readable for audit.

## Templates

GET `/templates` returns five real materializable templates. POST `/{id}/versions` with `{"template":"linux","target_ids":["<ssh-target-uuid>"]}`. Linux uses the fixed Python collector already shipped with SSH; Windows uses the PowerShell CIM collector. `snmp`, `proxmox`, `vmmanager` templates are restricted `connector` language JSON plans referring to existing named inventory collectors in inspect mode; they cannot select arbitrary URLs, OIDs or operations. No source substitution. The templates create immutable drafts, not automatically trusted code. Their existing underlying collectors continue to run through Connector Framework independently of this registry.

The registry supports Bash/Python local or SSH, PowerShell WinRM, and the three connector plan providers. Parameters are integer (bounded), string (length/optional enum) or boolean, max 32; unknown fields are rejected, and values never get interpolated into source. Source code is visible to readers: **do not embed secrets in source or parameter values**. The offline signer requires a trusted local workstation and does not make signed code safe.

## Limitations and verification

No user-supplied code is executed in 0.5.2. `bin/run-script.php` fails closed. Signing proves integrity and provenance, not read-only behavior. Script execution, isolation, Vault-backed execution delegation, output parsing and history are subsequent stages. No scheduled script execution or automatic execution after approval. UI is a basic working registry console, not the final 0.5.9 data-collection admin UI.

Run `php tests/script-registry-smoke.php`; it tests Ed25519, tampering, typed parameters, actual template materialization and DI/routes. `tests/script-registry-postgres-integration.php` is an isolated PostgreSQL 17+ test (requires `CAJEER_PG_TEST=1`, `CAJEER_PG_TEST_DATABASE=cajeer_test_*`, host/port/username/password/sslmode as in CI). Tests verify database migration, signing, MFA approval, archive, isolation, immutable source and key revocation. Full browser build and integration require a staging installation. The release channel remains development until strict verification succeeds.
