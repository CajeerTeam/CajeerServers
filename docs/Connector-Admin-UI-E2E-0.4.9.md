# 0.4.9 — Connector Admin UI & E2E

Версия обновляет существующую `/connectors`, не создавая параллельный runtime. Выберите Workspace, создайте target, выберите Inventory asset и совместимый активный credential. Для удалённого исполнения нужен также Inventory binding того же credential; галочка в форме привязки создаёт её автоматически. Если запись не входит в первые 100 credentials, можно ввести UUID из Vault. Поиск Inventory asset выполняется на сервере. После создания откройте настройки, проверку доступности, Discovery preview и sync. Разрешение конфликтов и связь с Inventory доступны в разделе ресурсов. Target deep link: `/connectors?workspace_id=<uuid>&target_id=<uuid>`; сервер проверяет членство в Workspace.

## Фоновые операции и расписания

- В «Разрешения и расписания» выберите health, inspect или sync. Введите срок (60–2592000 секунд), при необходимости интервал (60–86400 секунд), пароль и свежий TOTP. Выдаётся ограниченный сервисный grant. Новая версия target или credential требует нового разрешения. Scheduler запускает работу без браузерной сессии.
- В «Запуски» выберите действующее своё разрешение, поставьте job в очередь. Список, статус, попытки, код ошибки и результат читаются из серверного API. История обновляется каждые 5 секунд, при скрытой вкладке опрос прекращается; для queued/running доступна отмена. Остановка расписания — отзыв grant. Перепланирование — отзыв и выдача нового grant. Разрешения/источники отображают до 100 последних записей по существующим API, runs/events/actions/targets/resources имеют пагинацию.
- В «Webhook и события» создайте источник с действующим sync grant; ключ показывается однократно, закройте его после копирования. Ротация немедленно аннулирует старый ключ. История dispatch и dead-letter/redrive используют настоящую очередь. События не меняют Inventory напрямую. См. [протокол подписи](Connector-Events-0.4.7.md).
- В «Удалённые действия» выбираются обнаруженные QEMU VM с корректным mapping. Серверная политика `CONNECTOR_WRITE_ACTIONS` выключена по умолчанию. При разрешённой операции введите точное `vm.start qemu:101` (или shutdown) и свежий MFA. Для проверки UPID нужен новый MFA. Если результат неопределённый — проверьте Proxmox вручную и введите `I verified the remote result`; повторная отправка не выполняется. Клиент не повторяет write-запросы автоматически, ключ идемпотентности сохраняется в памяти для ручного повторения того же запроса при ошибке доставки. После перезагрузки сначала проверьте историю, прежде чем инициировать новую операцию.

Все операции остаются защищены серверными RBAC, Workspace isolation, CSRF, ETag и Vault. UI не является границей безопасности. Новых миграций нет. Серверные GET targets поддерживают search/provider/state; drivers возвращает `write_actions_enabled`, bindings — metadata `credential_version`, run history — `operation`. Схема enqueue остаётся `{id,deduplicated}`; для полного статуса используйте GET run.

## Изолированный E2E

Нужны установленный staging с PostgreSQL 17+, PHP 8.4+, Vault, Nuxt, активным Scheduler и connector worker. Не используйте production. Сценарий создаёт отдельный workspace, fixture credential и тестового viewer; он отзывает доступы в finally, но база со всеми тестовыми записями должна быть уничтожена после теста. Действия выполняются только на поставляемом синтетическом Proxmox fixture, не на настоящей VM.

1. На отдельном адресе из management-сети staging запустите `python3 tests/connector-e2e-fixture.py --bind <management-ip> --port 8443 --cert /path/cert.pem --key /path/key.pem`. Сертификат должен иметь SAN DNS/IP fixture. Fixture не управляет гипервизором, имеет только один тестовый VMID 101 и синтетический токен. Не выставляйте его в публичную сеть.
2. На staging PHP настройте `CONNECTOR_ALLOWED_NETWORKS`, `PROXMOX_CA_FILE` (доверенный CA fixture), `CONNECTOR_WRITE_ACTIONS=true`. Проверьте доступность DNS/IP fixture именно из PHP worker. Запустите Scheduler и worker с интервалом не больше 5–10 секунд. В staging разрешите права администратора, Vault MFA и создание Workspace/roles/users. Учётная запись должна быть выделенной для E2E, с включённым TOTP; часы runner и сервера синхронизированы.
3. Передайте переменные через безопасные secrets CI или окружение (не коммитьте пароль/seed): `E2E_BASE_URL`, `E2E_ADMIN_EMAIL`, `E2E_ADMIN_PASSWORD`, `E2E_ADMIN_TOTP_SECRET` (Base32), `E2E_ISOLATED_STAGING=1`, `E2E_ALLOW_WRITES=1`, `E2E_CONNECTOR_UI=1`, `E2E_CONNECTOR_FIXTURE_HOST`, `E2E_CONNECTOR_FIXTURE_PORT=8443`, `E2E_CONNECTOR_FIXTURE_PIN` (SHA-256 DER сертификата fixture, 64 строчных hex-символа; с 0.6.6 обязателен). Для старых тестов без включённого MFA seed не требуется; один статический TOTP не подходит для нескольких входов. Новый helper ждёт следующий 30-секундный слот, так как сервер запрещает повторное использование кода.
4. В `admin`: `npm ci`, `npx playwright install --with-deps chromium`, `npm run test:e2e:preflight`, `npx playwright test tests/e2e/connector-lifecycle.spec.ts`. Workflow `.github/workflows/e2e-staging.yml` запускает весь набор тестов при явном подтверждении disposable staging. Trace, video и screenshot выключены, чтобы не сохранять пароли/TOTP/одноразовые ключи.
5. После теста уничтожьте disposable БД и fixture. Не используйте synthetic credential или write-actions настройки на production.

## Проверки

`php scripts/verify-release.php` — локальные PHP smoke и UI policy tests. `php scripts/verify-release.php --strict` дополнительно требует настоящие PostgreSQL/Redis, установленные lockfile dependencies, Nuxt build/typecheck и настроенный disposable browser E2E. Без этого стабильный release не подтверждён. `bash tests/connector-sdk-integration.sh` проверяет TS SDK через настоящий HTTPS. Fixture работает по настоящему TLS и проверяет авторизацию, GET discovery, POST power и GET task status, но не заменяет испытания на реальном Proxmox. Полный браузерный тест требует установленного стенда; не подменяет API через `page.route`.
