# Stable Core Release Candidate — 0.9.9

Feature freeze: no new infrastructure providers, database schema changes or user-facing feature groups. This candidate remains `development` until full acceptance of the exact sealed build. No previous migration may be edited. Upgrade from 0.9.8 requires the exact source installation marker and retained release; use the offline procedure in `Installation-Upgrade-Migration-0.9.2.md`. All 64 migrations remain unchanged.

## Build and seal

Supported acceptance matrix: PHP 8.4/8.5, PostgreSQL 17/18, Redis 7; Node and npm/Composer as specified by `.nvmrc` and `scripts/build-toolchain.sh`; Linux x86-64 CPython 3.12 for the locked SSH agent profile. Browser tests run on Chromium via the reviewed Playwright lock. These are target environments, not claims of successful certification.

1. On a trusted network-connected Linux build host, run `bash scripts/resolve-dependencies.sh` if Composer/Admin locks are absent. Review the generated locks and commit them. The SDK lock is already committed. Do not bypass audits or change dependencies during acceptance.
2. From a clean committed checkout, `bash scripts/build-release.sh` runs dependency audits, locked installs, PHP/SDK/Nuxt builds and regression suites. The resulting build report now also includes all installed vendor file hashes.
3. Run `python3 scripts/candidate-release.py seal`. This checks the commit, build report and every hashed build input/output; it packages tracked source, Composer vendor, Nuxt `.output` and SDK `dist` into `storage/tmp/candidate/release-candidate.tar.gz`. It also emits `release-candidate.sha256`, `.release-candidate.json` and `release-candidate.cdx.json` (CycloneDX 1.6 dependency inventory of reviewed Composer/npm/Python locks, including dev/optional packages, not an OS or system library SBOM). Tar metadata is normalized; this is not a claim that all Nuxt output is reproducible across environments.
4. Publish the archive and its checksum through a trusted channel. The hash is not a signature; keep the manifest/checksum separately trusted. On staging, verify the archive SHA-256, extract into a NEW empty release directory (never over production), then run `python3 scripts/candidate-release.py verify --root /opt/cajeer-releases/0.9.9`. Compare the returned candidate ID to the seal output (or supply `--expected-id TRUSTED_SHA256`). The verifier checks every listed file, file size/executable bit, additional files in executable runtime trees and build output, and SBOM digest. It rejects symlinks in packaged source/output. Do not replace the marker manually to make an unrelated build appear valid.
5. Configure `.env`, writable storage, APP_KEY, Vault key, trust profiles and Python environment separately. Candidate archive does not contain instance secrets or runtime data. For strict release verification on the build/acceptance host, keep the reviewed dependencies and full checkout (including SDK and Admin node_modules); the sealed deployment bundle intentionally does not contain Admin build-time node_modules or the Python virtualenv. Verify again after staging deployment and after acceptance. Keep code and marker read-only to the service account. `/api/v1/system` returns only an optional opaque `candidate_id` (SHA-256 of the sealed manifest), not the contents. This identifies the deployed manifest, not remote attestation of each file; operator verification is mandatory.

## Full acceptance

Use an acceptance host with filesystem access to the separate deployed staging release directory (locally or via a trusted read-only mount), the clean source checkout and original sealed build outputs, installed dependencies, isolated test PostgreSQL/Redis, the separately installed test database, and owned live provider devices. Set all existing strict verifier variables (see previous release docs), including all browser flags, fixture TLS pin, administrator MFA credentials, `CAJEER_SMOKE_URL` and `E2E_BASE_URL` to the SAME disposable staging origin. Deploy the sealed archive there and start all workers/scheduler. Run the 17 browser specs / 21 tests with no skips or retries. Windows native probe and both PHP/PostgreSQL CI matrix jobs must also pass on the same commit; review their authenticated CI evidence separately. Exercise the configured benchmark and backup/restore drill on separate staging infrastructure, verify scheduler/connector success and alert delivery; review security findings and API compatibility. The seal itself is not an acceptance result.

```sh
python3 scripts/candidate-release.py accept \
  --manifest storage/tmp/candidate/.release-candidate.json \
  --deployment-root /opt/cajeer-releases/0.9.9 \
  --report /secure/acceptance-0.9.9.json
```

The command validates the local build against the manifest and archive checksum, checks the actual staging release files before and after the run and the public staging candidate identity, invokes the complete existing `verify-release.php --strict` with `CAJEER_CANDIDATE_ID`, then runs a 72-hour monotonic soak with read-only system/readiness/login probes every minute. Any failed probe, identity mismatch, redirect, excessive monitoring gap, strict test failure or changed source/manifest/archive aborts. No success report is emitted on failure; an earlier report at the supplied path is removed before validation. The report is scoped to strict verification and HTTP soak (`promotion_ready: false` until independent release review). It records commit, manifest and archive hashes, elapsed soak and probe count. Run in a supervised long-lived terminal/service on the acceptance host; hosted CI job time limits are too short for 72 hours. A failed or interrupted run must restart. HTTP soak verifies availability, not connector throughput, data integrity on every interval or DR RPO: run the existing benchmark, operational metrics and recovery checks separately. No automatic switch to stable; promotion requires operator review of all actual acceptance evidence and independent security review.

## Upgrade

Stop old processes, keep the previous full code release, configuration and storage. Enable maintenance, then `php bin/cajeer upgrade:apply --previous=/opt/cajeer-releases/0.9.8 --archive=/secure/pre-upgrade-0.9.8.cjdr --key-file=/secure/backup.key --offline`. Verify migrations/CMDB and readiness before disabling maintenance. No new SQL migration. An older installation must first follow its supported upgrade sequence; the current marker must match 0.9.8 when beginning a new upgrade. Existing journal resume/recovery is unchanged.

## Remaining blockers

The supplied 0.9.8 tree does not contain `composer.lock` or `admin/package-lock.json`. No synthetic lockfiles are added. Full sealed candidate creation, strict verification, live hardware acceptance, browser tests and 72-hour soak require the real build/staging environment. Native regressions exercise the sealer and HTTP probe against disposable Git/HTTP fixtures only. The `development` channel is intentional.
